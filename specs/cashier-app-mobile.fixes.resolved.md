# Fixes for specs/cashier-app-mobile.md

Generated by an independent review pass (see review output for full detail).
One root-cause bug was found; it is listed once with all the spec items it
breaks, per the review-faq fix-file format.

## Fix 1 — Tax rate is stored as a percentage but consumed as a raw fraction

**Spec items affected:**
- Requirement 12 ("SETTING includes: ... tax rate (optional)")
- Requirement 3 ("... running transaction total shown live ...")
- Requirement 4 ("... KONFIRMASI enabled only when cash paid ≥ total")
- Requirement 6 ("... matching the original's receipt content: ... subtotal, cash paid, change ...", tax line specifically)
- Definition of Done: "KASIR replicates: ... live running total"
- Definition of Done: "SETTING supports store info, receipt footer, tax rate, printer width, and Bluetooth printer selection"

**Gap (what's wrong):**

`src/screens/setting/SettingScreen.tsx` labels the field "Pajak (%)" (line 142)
and stores whatever the user types directly as `settings.taxRate` with no
conversion (line 55: `taxRate: parseFloat(taxRate) || 0`). A user entering
`10` to mean "10%" ends up with `settings.taxRate === 10` in the `settings`
table.

That raw value is then used as a direct multiplier — not a percentage — in
`src/db/repositories/transactionRepo.ts`, line 131:

```ts
const taxTotal = round2(subtotal * (taxRate || 0));
```

and `taxRate` itself is passed straight through from
`src/screens/kasir/KasirScreen.tsx` line 55:

```ts
const taxRate = settings?.taxRate ?? 0;
```

with no `/100` anywhere in the codebase (confirmed via grep — the only
`/100`-shaped operation in `src` is unrelated rounding in
`src/domain/pricing.ts`).

Concretely: if a store sets a 10% tax rate and a customer buys Rp 20.000 of
goods, the code computes `taxTotal = 20000 * 10 = 200000` (a 200.000 rupiah
"tax" on a 20.000 rupiah subtotal) instead of the correct Rp 2.000. The
transaction total becomes Rp 220.000 instead of Rp 22.000 — an ~10x
overcharge whenever tax is configured to any nonzero value. This is live in:
KASIR's running total, the Payment screen's total/KONFIRMASI gate, and the
printed/previewed receipt's "Pajak" and "TOTAL" lines.

No test in `__tests__/` exercises a nonzero tax rate — `receipt.test.ts`
hardcodes `taxRate: 0`, and `pricing.test.ts`/`money.test.ts` don't touch tax
at all, so this went unverified.

**Fix:**

Pick one unit for `Settings.taxRate` and apply it consistently at the single
point where tax is computed. Recommended: keep the Setting-screen UI in
"percent" terms (unchanged, since the label already says "%"), but convert to
a fraction where it's actually applied — `recomputeTotals` in
`src/db/repositories/transactionRepo.ts`:

```ts
const taxTotal = round2(subtotal * ((taxRate || 0) / 100));
```

Also add a code comment on `Settings.taxRate` in `src/types/index.ts`
documenting the unit (stored/edited as a percentage, e.g. `10` means 10%) so
future call sites don't reintroduce the mismatch. Then add a regression test
in `__tests__/pricing.test.ts` or a new `__tests__/transactionRepo.test.ts`
(if repo-level testing is set up with a real/mocked SQLite that returns rows)
asserting that a 10% tax rate on a 20000 subtotal yields a 2000 taxTotal and
22000 total — so this can't silently regress again.
